# 小型 Linux 运维团队试用计划

设计日期：2026-10-18。目标用户由项目负责人确认：Linux 运维／小型企业内网团队。当前没有实际客户访谈、生产日志样本或付费记录。本文件是可执行的招募和试用方案，不能表述为需求已经得到验证。

## 本轮要回答的决策

是否值得继续完善“本地 SSH 异常调查助手”，以及哪部分能减少运维人员的实际工作。试用围绕一台授权 Linux 主机、一个登录异常场景进行，以只读报告为交付；结论仍由运维人员确认。

## 参与者和责任

- 项目负责人：邀请参与者、确认范围、整理反馈和决定是否继续投入。
- 试用团队联系人：确认主机和日志访问授权、选择可使用的案例、解释维护和正常活动。
- 案例复核人：核对报告，不应仅依赖模型判断；标记尚无法确定的案例。

建议首轮邀请1～2个团队，每个团队选5～10个授权历史案例，包含正常维护、凭据错误和需要调查的异常。这个数量是控制投入的操作建议，不是统计样本量结论；不能凭它估计普遍检出率或市场规模。

## 执行步骤

1. **20分钟访谈。** 用访谈提纲了解最近一次真实登录异常如何处理，确认最耗时步骤、现有工具和数据限制。不先要求对方认可多模型方案。
2. **确定有限范围。** 写下数据来源、授权人、保存期限、可展示内容和结束后的清理责任。原日志在客户本地；反馈使用匿名团队/案例编号。
3. **记录现有工作方式。** 保留现有处理时间、使用的证据、最后结论和仍未知的信息；不能把模型判断当作参考答案。
4. **运行只读调查报告。** 先使用程序事实报告，再按团队选择加入本地模型。记录安装时间、异常退出和需要人工纠正的内容。
5. **复核实际价值。** 问清楚哪些内容被使用、哪些被忽略、是否愿意拿另一个案例继续使用，以及是否愿意为部署维护或节省的工作付费。
6. **做继续/调整/暂停决定。** 依据指标和具体案例，不依据点赞、模型数量或演示是否顺利。

时间安排可用一周完成首次访谈与少量案例，再按参与者可用时间安排下一轮；不是承诺在一周内得到商业结论。

## 比较方法

人工流程、程序事实报告和模型辅助流程应保留同样的业务范围。可使用复杂度相近的案例分组，或由不同复核人处理相同案例并交叉安排顺序。避免同一人刚做完一个案例，又立刻用工具重复处理后直接把速度提升归因于工具。

小样本中应保留逐案例记录、失败和超时案例，报告分母与缺失值。若规则或上下文在试用中改变，记录版本，不把前后不同条件混成一个“提升率”。

## 可直接使用的邀请文字

我们在做一个本地运行的 Linux 登录异常调查工具，想了解它能否减少运维人员翻日志和核对证据的时间。希望找一个小范围、只读的试用场景：日志留在你们环境，工具输出事实、待核对假设和缺失信息，由你们确认结论。能否先用20分钟聊一下最近一次类似问题是怎样处理的？现阶段是早期试用，没有经过生产准确率或合规认证。

这段文字仅供项目负责人自行发送；本轮没有向任何团队发送邀请。
